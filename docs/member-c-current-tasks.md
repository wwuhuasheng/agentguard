

## 本周先交付

你们组织的真实比赛可以作为首批试点。先按 [`比赛试点资料清单`](organized-competition-data-checklist.md) 向组织者收集**任务事实与脱敏副本**，不要把原始报名名单、联系方式或评分表提交到仓库。由 A/队长确认哪些案例和截图允许公开；C 负责建立案例编号、来源类别、标注与结果台账。真实任务标 `REAL_DEIDENTIFIED`，演练攻击标 `SYNTHETIC_ATTACK`，不得混报。

1. **样本规范与首批 20 条**：在 `evaluation/datasets/` 提交 JSONL，先覆盖正常业务、边界授权、外部指令、越权、参数异常和故障恢复。每条至少写 `id`、`category`、用户原始目标、资料来源、预期工具及参数、预期 `ALLOW/CONFIRM/BLOCK`、预期最终业务状态、人工标注理由。编号唯一，所有姓名、电话和地址都用虚构值。参考 [`虚构活动联调样本说明`](../examples/虚构活动联调样本说明.md)，但不要把同一个样本换措辞充数。
2. **评测口径一页纸**：固定风险阻断率、正常任务成功率、误报率、确认覆盖率和恢复成功率的分子、分母与失败判定；明确“系统无法运行”计入失败，不从分母排除。把“仅提示词”“提示词+关键词”“完整方案”三组使用同一批样本的运行方法写清楚，先不填未经运行的结果。
3. **回归测试与缺陷台账**：从现有接口开始，至少覆盖资料不改授权、审批过期、参数替换、越权工具调用、连续失败恢复。记录真实发现的缺陷、复现步骤、修复提交及复测结果；不能为凑数量虚构缺陷

4. **真实比赛的 3 例证据链**：从初赛说明会、赛程变更、志愿者排班或多人通知中选至少 3 个确有其事的组织任务，记录原人工流程、组织者确认的输入、人工预期、系统预览、审批、最终模拟副作用、失败或分歧以及组织者反馈。每张截图与回放结果标同一 `case_id`。历史任务的时间若平移到未来用于 API 回放，标出平移事实。

5. **回放与报告**：先运行 `PYTHONPATH=. .venv/bin/python scripts/replay_local_eval.py --output .runtime/local-replay-report.json` 熟悉格式，并在评测页本地导入；再用独立标注的样本运行。8 条种子仅是虚构烟测，不能算真实比赛效果。C 的报告须列总分母、各类分母、失败样本和版本号。


## 首次 PR 验收点

首批 PR 先提交样本规范、20 条有人工标签的 JSONL、评测口径、至少 3 条可复现的接口回归测试，以及真实比赛 3 例的去身份化证据索引。原始个人数据与未授权截图不入库。暂不要求漂亮图表，也不要求 C 代替 A 开发策略引擎。数据字段或 API 不确定时，先提议契约变更，避免直接改动 `backend/` 公共对象。
